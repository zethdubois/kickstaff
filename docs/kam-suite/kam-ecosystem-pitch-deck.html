Kickagent + kickstaff

KAM Suite — one product, two roles

Arrow keys / space to advance · Esc for overview

The usual integration tax

  • Publish a REST API, maintain docs, ship SDK versions
  • Consumers redeploy when something new ships
  • Documentation drifts from reality
  • Versioning pressure on both sides
  • Everyone waits on everyone else

A different shape

Operations live inside the product — without asking users to notice two applications.

kickstaff

Host · shell · trust boundary

kickagent

Provider · capabilities · ops depth

kickstaff — the host

  • What people log into: marketing, admin, ops hub
  • KAM console: palette, logs, session
  • Authentication, layouts, product chrome
  • Owns how it looks and who is allowed in

kickagent — the provider

  • KAM commands, business logic, data pipelines
  • Bills, units, ETL, long-running jobs (over time)
  • No browser UI — publishes capabilities
  • Owns what the product can do operationally

How updates flow

One command catalog → Publish manifest
(catalog + integrity) → Host reload → Palette & hub update

Handler fixes can land without rebuilding the entire web app for every kickagent release.

Why teams care

  • Faster iteration on operational features
  • Single source of truth for which commands exist
  • No parallel wiki per new command
  • Clear ownership: kickagent:* in KAM → kickagent; pages & auth → kickstaff

What we do not claim

  • Not magic “zero deploy” for everything
  • Host still owns sign-in, routes, and product chrome
  • Some features still need host UI (e.g. new resource views)
  • Routine loop stays on the provider: ship → publish → reload

What is next

  • Today: published manifest + dynamic plugin load
  • Roadmap: long-running job API and streaming (not shipped yet)
